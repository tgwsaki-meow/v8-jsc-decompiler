# O1 — is the output an equivalent program?

The project's open question, and until now the only one with no number against
real input. `5095` holes carried by `1.28%` of 239 979 functions says "nearly
done"; `51.33%` opcode match on 45 synthetic fixtures says "halfway". Both
cannot describe the same artefact, and the resolution is that **holes do not
predict equivalence**: a function with no holes can still evaluate things in
the wrong order, the wrong number of times, or through the wrong implicit
conversion. This document replaces the proxy.

Everything below is produced by

```
node tools/verify/o1_corpus_selftest.mjs            # does the instrument work
node tools/verify/o1_corpus.mjs --jobs 2 --stride 4 # the measurement
```

and the oracle is `src/verify/o1_corpus.mjs`.

---

## 1. Why this could not be measured before, and what changed

`src/verify/o1_bytecode.mjs` states the blocker in its header: both of its
streams come from a real V8 through `--print-bytecode`, a V8 run **executes**
the script after printing it, and there is no compile-only `--print-bytecode`.
`docs/ARCHITECTURE.md` §7 forbids running corpus code outright, so fixture O1
is restricted to code we wrote.

The blocker is the *printing*, not the comparing. Neither side of the
comparison has to be executed:

```
stream A   corpus .jsc                                 ──our decoder──→  bytecode
stream B   our output ──compile only──→ .jsc           ──our decoder──→  bytecode
                        normalise, pair, compare, classify
```

Three facts make that work, and each is measured rather than assumed.

**Our decoder is sound enough to be the instrument.**
`tools/disasm/oracle_agreement.mjs` measured `src/disasm` **instruction-exact
on 1680/1680 functions** against V8's own listing, and `tests/t4/acceptance.mjs`
is 1200 assertions / 0 failures. Both streams go through that one decoder and
one normaliser, so a decoder bug cancels instead of biasing. The trade is the
opposite of `o1_bytecode.mjs`'s: that one gets engine truth and pays by having
to run the program; this one keeps the program unrun and pays by trusting the
decoder — which is the thing T4/T5 already spent their acceptance budget
proving.

**Compile-without-execute already existed.** `tests/t4/make-cache.cjs` and
`src/verify/mint.mjs` use `new vm.Script(src, {produceCachedData:true})` /
`createCachedData()`, and make-cache.cjs's own comment states the part that
matters: *it deliberately does not run the script, and under `--no-lazy` every
function is compiled during `new vm.Script`.* Measured here, on a two-inner-
function script: without `--no-lazy` the cache carries **1** BytecodeArray,
with it **4**. Over a 40-declaration/40-arrow script: **1** against **81**.
The flag is load-bearing and self-test check F asserts both halves.

**Stream B is minted by the corpus's own V8.** Electron 40.0.0 ships V8
14.4.258.16, the corpus's exact version, and `ELECTRON_RUN_AS_NODE=1` turns it
into a node. Verified on this host: the minted header is
`magic 0xc0de0674 / versionHash 0x12819a30`, bit-for-bit the corpus's own, and
the child reports `v8: 14.4.258.16-electron.0`. The oracle **refuses to
compare** two caches whose `versionHash` disagrees (`status:
version-mismatch`), because minting with the local node — V8 14.6.202.34,
where six comparison bytecodes changed operand type (ARCHITECTURE.md §1.3) —
would blame version drift on the decompiler.

`.v8bin-cache/electron-v40.0.0-win32-x64/` had only the two snapshot blobs:
`tools/oracle/fetch_electron.mjs` extracts just those, by design, because its
job was the read-only-heap checksum. The minter needs the binary, so
`electron.exe` was extracted from the archive already in the cache. If it is
missing the runner exits 2 and says so rather than silently falling back to
the local node.

`--no-lazy` is also the right match for the producer: §9.4 measured the corpus
as fully eager — 239 979 SFI, 239 979 BytecodeArray, **0 UncompiledData**. The
cache *flag* hash differs between the two sides because the corpus was not
produced with `--no-lazy`; that hash gates cache acceptance inside V8 and has
no effect on the bytecode of a function, so it is reported, not asserted (257
of 260 files).

The last way the two sides could be incomparable is a kind mismatch: a module
and a script compile the same text differently, and stream B is always minted
as a classic sloppy script. Checked across the whole corpus from the
`sourceHash` bits of each header: **1039 scripts, 0 modules, 0 with wrapped
arguments.** So there is no file for which the mint kind is wrong.

## 2. Execution policy

Nothing from `extracted_jsc/`, `decompiled_js/` or `linuxQQ/`, and nothing
derived from them, is executed. This is asserted in code, in the spirit of
`src/verify/corpus.mjs::assertExecutable` but for the opposite direction:

| assert | refuses |
|---|---|
| `assertCompileOnlySpawn(argv)` | any child but `src/verify/mint_child.cjs`, whose entire body is `new vm.Script(…, {produceCachedData:true})` / `createCachedData()` — no `runInThisContext`, no `vm.runInNewContext`, no module linking |
| same | any engine flag that evaluates instead of compiling (`-e`, `--eval`, `-p`, `--print`, `--print-bytecode`, `-r`, `--require`, `--import`, `--input-type`) |
| `assertNeverExecuted(p)` | a corpus path in the *script position* of a spawn |
| `assertNotInExecutableTree(p)` | writing any corpus-derived artefact under `scratch/t3/work`, because `corpus.mjs::WORK_ROOTS` declares that tree executable for O3 |

The work directory is therefore `scratch/o1corpus/`, deliberately outside the
tree another tool in this repo would run. Self-test section D exercises all
four refusals. The oracle never imports `src/verify/oracle.mjs` or
`tools/oracle/engines.mjs`, the two modules that can start an engine on a
script.

Layering (ARCHITECTURE.md §11.0) is unchanged: `src/verify/o1_corpus.mjs` and
`tools/verify/**` import from `src/`, never the reverse, and the decompilation
path gained no dependency on the verification side.

## 3. What the normalisation erases, and why each erasure is defensible

This is where the measurement could quietly become meaningless, so every
erasure is named, argued and **counted**.

### 3.1 Inherited from `src/verify/normalize.mjs`

`normalize.mjs` already erases four things and argues each in its header; the
same code runs over both streams here, reached by rendering our
`Instruction[]` into the parser's structure with
`src/disasm/format.mjs::toParsedForm`. Using the existing normaliser rather
than writing a second one for our side is the point: two normalisers could
drift, one cannot.

| erased | replaced by | why it is incidental |
|---|---|---|
| local register numbers | first-appearance identity classes `R0, R1, …` | frame slot indices shift when an unrelated earlier expression changes; the def/use relation is what carries meaning and a first-appearance bijection preserves exactly that. **Parameter registers `a0, a1` are kept** — `a0` ≠ `a1` is semantics. |
| feedback vector slot indices | `FB[*]` | slots are allocated by a running counter over preceding feedback-consuming operations; the index identifies nothing about the operation. The *presence* of the operand is kept, so gaining or losing one still compares unequal. |
| constant pool indices | the resolved value, `K("m")` | the index is a position in a pool built in emission order; the value is the semantics. |
| absolute jump offsets | labels, with `L0:` on the target | byte distances move with instruction width. The label is derived from the engine's own resolved target, and the marker on the target instruction is what makes the erasure lossless — without it two different control-flow graphs could collapse to one token list. |
| `.Wide` / `.ExtraWide` | dropped | a width artefact of the four values above. |
| `Star0`…`Star15` | long form `Star Rn` | `SHORT_STAR_BYTECODE_LIST` encodes the register in the *opcode*; without this a register-allocation shift would change the opcode and defeat the register rule. |
| source positions | excluded | character offsets into source text; renaming one variable shifts every later one. |

### 3.2 Added here: per-cache object ids

Applied to two caches from two different serializer runs, the above is not
quite enough. `src/disasm/format.mjs::renderConstant` prints a heap-object
constant as

```
<SharedFunctionInfo #123 foo>      <ScopeInfo #45 BLOCK_SCOPE>
```

and `#123` is `src/heap`'s object id — the slot that object happens to occupy
in *that* cache's graph. V8's own listing prints no such number
(`<SharedFunctionInfo foo>`); our renderer adds it because a human reading a
decoder dump wants it. Comparing it across two caches compares two unrelated
counters, so **every function that creates a closure would mismatch** for a
reason with nothing to do with the program.

`eraseAllocationIds()` rewrites `#<digits>` to `#*` inside a `<…>` descriptor,
on both streams, and the count is reported. The descriptor's type and name
survive, which is what carries meaning: `<SharedFunctionInfo #* foo>` still
differs from `<SharedFunctionInfo #* bar>` and from
`<ScopeInfo #* BLOCK_SCOPE>`.

Self-test check A is the proof that this is sufficient and that nothing else
is needed: the same program minted twice — once as written, once with a leading
newline, so the two caches differ in bytes, in every source position and in
every object id — must normalise to **identical** streams for every function.
It does.

### 3.3 Reported, not erased: the name inside a closure descriptor

`CreateClosure` names its target's SFI, and the name of an anonymous function
literal is information the `.jsc` does not carry — the emitter has to invent
one to emit a declaration at all. That is exactly the class of loss the owner
accepts as unrecoverable. Erasing it silently would also hide a real renaming
of a *named* function.

So both numbers are reported and neither is folded into the other:
`exactFunctions` keeps the name, `exactModuloClosureNames` erases it, and the
gap between them is the whole cost of that decision. On this sample the gap is
**zero** — no function differs only by an invented name — so the question turns
out not to matter yet.

### 3.4 Kept, deliberately, though erasing them would raise the number

Opcode; operand arity and kind order; parameter registers; `<context>`,
`<closure>`, `<this>`, `<new.target>`; register-range lengths (the range start
is mapped through the register bijection, the *length* carries the call
arity); flag immediates (`#29` — real object-literal shape bits); non-jump
immediates (`LdaSmi [1]`, `LdaImmutableCurrentContextSlot [2]` — the context
slot index is semantics, not allocation); runtime and intrinsic callee names;
handler table ranges, mapped onto instruction-index space; parameter count.

### 3.5 The blind spot: real on the fixture path, self-inflicted here, now closed

V8 prints an array or object literal as
`<ArrayBoilerplateDescription PACKED_SMI_ELEMENTS, <FixedArray[3]>>` and never
prints the element values (`tools/probes/probe_pool.mjs` verified it on node
with the pool dumped and on d8 with it partial). For `o1_bytecode.mjs`, whose
stream A **is** a real V8 listing, that is final: a difference confined to
literal element values cannot appear in the text it reads, and its
`blindSpot` declaration still says so.

**It was never final on this path, and earlier versions of this section were
wrong to say it was.** Both streams here come from our own decoder, and the
decoder reads the values: `src/heap/objects.mjs::decodeArrayBoilerplate`
returns `elements`, `decodeObjectBoilerplate` returns `entries`, and
`DeclareGlobals`'s operand arrives decoded as `{t:'array',
className:'FixedArray', values:[sfi, slot, "topVar", …]}`. They were discarded
one layer later, by `src/disasm/format.mjs::renderConstant`, which prints a
length and no contents — correctly, because that function's output is measured
against V8's own listing instruction-exact by
`tools/disasm/oracle_agreement.mjs` (1680/1680 functions) and V8 prints no
values there. So the blind spot on this path was code reuse, not an engine
limit, and closing it cost no execution and no new oracle.

Both streams are now rendered with `toParsedForm(…, {literalValues: true})`,
which routes constants through a **second** renderer, `renderConstantDeep`.
The default renderer is untouched, so the V8-agreement measurement — the one
thing that makes "both streams through one decoder" an argument rather than an
assumption — is unaffected; `src/verify/normalize.mjs` is untouched for the
same reason, since `oracle_agreement.mjs` normalises with it. What that
renderer adds:

| now compared | spelling |
|---|---|
| array literal elements, recursively | `<ArrayBoilerplateDescription PACKED_SMI_ELEMENTS[3] [1, 2, 3]>` |
| the elements **kind** | `[1,,3]` is `HOLEY_SMI_ELEMENTS` where `[1,2,3]` is `PACKED_SMI_ELEMENTS` |
| object literal keys and values, recursively | `<ObjectBoilerplateDescription[2] {"x": 1, "y": "two"}>` |
| an object-literal value V8 computes at runtime | `<the_hole>`, distinct from a value |
| the `DeclareGlobals` declaration list | `<FixedArray[6] [<SharedFunctionInfo #*>, 0, "topVar", …]>` |
| a tagged template's raw and cooked strings | `<TemplateObjectDescription[2] raw=[…] cooked=[…]>` |
| a canonical empty literal | `<root empty_object_boilerplate_description>` |

Four residuals are left. Each is **counted per file** (`literalA` / `literalB`
in the raw report, summarised under "Literal element values"), so none of them
is an unqualified claim:

* **`refused.FixedDoubleArrayMap` — an array literal of nothing but doubles.**
  V8 stores those in a `FixedDoubleArray`, whose layout is
  `@cppObjectLayoutDefinition`, so `layouts.json` carries no class for it, and
  whose Torque element type (`float64_or_undefined_or_hole`) is a 9-byte struct
  against the 8-byte on-heap double, so the stride cannot be taken from the
  profile either. The decoder refuses by map name rather than guessing a
  stride, and the renderer prints
  `<ArrayBoilerplateDescription PACKED_DOUBLE_ELEMENTS !undecoded:FixedDoubleArrayMap>`.
  `[1.5,3.5]` against `[2.5,3.5]` therefore still compares **equal**, under
  that name. Self-test G pins it, so fixing it cannot pass unnoticed. The fix
  belongs in `tools/profilegen`: the stride is a fact about V8 and must come
  from the pinned sources, never from a literal in a reader.
* **`idsOmitted` — which function a declaration points at.** `src/heap` gives
  a `{t:'sfi'}` a per-cache object id and no name, so inside a container the id
  is erased at render time, in the same `#*` spelling `eraseAllocationIds` uses
  at the top level. Every declared **var** name is now compared (it is a string
  in the array), and so are the position and arity of every declared function;
  the identity of the declared function is not.
* **`hashed` — a container above the inline cap** (48 elements or 2048
  characters) is compared by a sha256 of its rendered contents. A difference is
  still **detected**; it is not legible in the diff.
* **A `#<digits>` inside a literal string**, e.g. `{color:"#333"}`, used to be
  rewritten by §3.2's id erasure, which would have made `["#333"]` and
  `["#334"]` compare equal. That erasure is quote-aware now and self-test G
  pins both halves. The one case it cannot resolve is a string containing an
  unescaped `"` — V8's own `PrintUC16` does not escape it — which makes the
  spans after it ambiguous; the scan stays deterministic, so the cost is
  precision inside such a string and never a false equality between streams.

O3 still sees more than this: the values of a `FixedDoubleArray` literal, and
which declared function is which, are things only the emitted text shows. Any
claim of equivalence from this document is therefore "equivalent up to
double-element literals, the identity of declared functions, and feedback slot
indices" — which is a much smaller caveat than the one this section used to
carry.

What it cost is measured, not asserted: **26 functions left `exact`** on the
full corpus, 15.0695% → 15.0478% of paired, and the first thing the new
visibility found is our emitter reordering the keys of an object literal.
§6.9 has both runs and all three residual counts.

## 4. Pairing

A match rate is only as good as the correspondence it is computed over, so the
mode is reported per pair and the rate is broken down by it.

Corpus O1 has one pairing key fixture O1 never had. `src/emit/index.mjs` keeps
an `emitName` map from `sfiId` to the identifier it gave that function, and it
reaches the oracle as `perFunction[].name`. Stream B is the compilation of
that very text, so V8's SFI name for the function **is** that identifier.
Pairing on it is identity by construction, not a similarity guess — the only
mode here whose number needs no caveat. It is reported as its own mode, `sfi`.

Whatever `sfi` does not cover is handed to `o1_bytecode.mjs::pairFunctions`
unchanged, which reports, per pair:

| mode | what it means | how much the number is worth |
|---|---|---|
| `sfi` | our emitter's own record of the name it gave that `sfiId` | identity |
| `name` | both sides print the same SFI name | strong |
| `greedy` | best opcode-similarity match among ≤24 leftovers on each side | a guess; circular, since similarity is also the thing being measured |
| `positional` | same index in the listing | order only |

Unpaired functions on either side are a **result**, never a dropped row:

* **A-side unpaired** = V8 produced this function from the original and did
  not produce it from our text.
* **B-side unpaired** = we emitted a function V8 did not produce from the
  original.

Section 6.3 shows that the A-side count is the single largest result in this
measurement, and §7 shows why it is a real absence rather than an artefact of
the mint.

## 5. How a divergence is classified

For every non-exact pair: trim the common prefix and suffix, run an LCS edit
script over the normalised instruction strings of what is left, group the
edits into hunks, and name each hunk's shape.

A one-for-one substitution is read directly. Anything else is reduced to the
**opcode multiset difference** first, with register moves (`Star`, `Ldar`,
`Mov`) set aside into a `moveDelta` that stays visible in the shape string.
The reason is empirical: read positionally, the top bucket was a
`replaced-block` holding 422 functions and saying nothing, because rewriting
`o.x` as `o[k]` is one opcode substitution plus two register moves for the new
key. The reduction is deliberately conservative — a hunk gets a named family
only when the difference reduces to **one opcode on each side, or none**;
otherwise it stays `replaced-block` with both opcode sets printed.

Named families include `compare-opcode` (`TestEqual` vs `TestEqualStrict` — a
real semantic change), `named-vs-keyed-property`, `define-vs-set-property`
(`{x: v}` vs `o.x = v`: `Define*OwnProperty` creates an own data property and
ignores a prototype setter, `Set*Property` does not),
`undefined-for-a-value`, `missing-tdz-check`
(`ThrowReferenceErrorIfHole`), `missing-context-store`, `context-store-form`,
`call-form`, `coercion-opcode`, `operand-order` (the operands are a
permutation — evaluation order changed), `register-class` (same opcode, a
different definition is read), `constant-value`, `jump-target`.

Self-test check C pins the classifier down against two divergences whose
answer is known independently: `===` → `==` must come out
`compare-opcode`, and `o.x` → `o[k]` must come out
`named-vs-keyed-property`. Both do. Without that check the ranked list could
be plausible labels attached to the wrong diffs — the first version of the
classifier failed the second case and was fixed.

### A divergence that is NOT visible, and therefore not a divergence

The prompt's example "`o.x` emitted as `o["x"]`" turns out not to exist as a
mismatch. V8's `BytecodeGenerator` classifies a property access by
`Property::key()->IsPropertyName()`, which is true for a string literal that
is not an array index, so `o["x"]` and `o.x` compile to the *same*
`GetNamedProperty`. Rewriting one as the other is invisible to this oracle
because it is invisible in the bytecode — it is a formatting difference, which
is the class of loss the owner already accepts. The real, visible case is
`o.x` against `o[k]` for a non-literal `k`, which is what the self-test uses.

**Every exact match in this measurement came from `sfi` pairing.** The weak

this measurement could have been quietly worthless.

The A-side unpaired count, 26.19%, is the second-largest result in this
document and is **not** a pairing failure: B-side unpaired is 0, so every
function stream B contains found a partner. Self-test check F establishes what
an A-side unpaired function means. With `--no-lazy`, a 40-declaration /
40-arrow script serialises **81 of 81** functions, and 100 declarations inside
one function serialise **102 of 102** once they are referenced — but **2 of 102**
when none of them is, because V8's scope analysis does not allocate the
variable of an unreferenced inner declaration, no `CreateClosure` is emitted,
and the SFI is unreachable from the parent's constant pool. So an A-side
unpaired function means **our text does not create that closure**: V8 made it
from the original and will not make it from ours. It is output loss, measured
at the only place it is visible.

### 6.5 One defect accounts for most of the list

Families 1, 2, 3, 4, 11, 15, 16, `context-store-form`, `missing-context-push`
and a large part of 6, 10 and 12 are one thing: **closure variables are
emitted as function-local declarations instead of as a shared scope.**

Measured directly, with no reference to the diff, on
`r_commonKitComponentXkitXDialog.jsc` — a file where A and B have the *same*
82 functions, so nothing here is confounded with the function loss of §6.3
(`tools/probes/probe_rootcause.mjs`):

| opcode | stream A | stream B |
|---|---:|---:|
| `CreateFunctionContext` | 4 | **0** |
| `CreateFunctionContextWithCells` | 6 | **0** |
| `PushContext` | 10 | **0** |
| `StaCurrentContextSlotNoCell` | 64 | **0** |
| `LdaImmutableCurrentContextSlot` | 123 | **0** |
| `LdaImmutableContextSlot` | 176 | **0** |
| `ThrowReferenceErrorIfHole` | 29 | **0** |
| `LdaUndefined` | 38 | **594** |
| `CreateClosure` | 81 | 80 |

Our output contains **no context operations at all**, and `LdaUndefined` goes
from 38 to 594. The emitter's own report already counts the consequence
without naming it: of 599 declared names, **136 are read but never written**.
The chain is:

1. a variable the original kept in a context becomes a `let` in each function
   that mentions it, so no context is created and no slot is written
   (`missing-context-*`, `context-*-form`);
2. each such declaration costs `LdaUndefined; Star rN` at function entry
   (`extra-load-store`, 12 842 functions);
3. a nested function that read the enclosing slot now reads its own freshly
   declared local, whose value is `undefined`
   (`undefined-for-a-value`, 16 726 functions);
4. the TDZ check that guarded the slot read has nothing to guard
   (`ThrowReferenceErrorIfHole` disappears — the top shape of family 1);
5. a closure the original created through a context slot is never created, so
   V8 does not compile it and stream B does not contain it
   (the 26.19% A-side unpaired of §6.3).

The minimal repro is two instructions long:

```diff
--- stream A: b_165background.jsc, function `Fn` (sfi 575), paired by `sfi`
+++ stream B: our output, recompiled
- LdaImmutableCurrentContextSlot [8]
- Return
+ LdaUndefined
+ Star R0
+ Return
```

`return <captured variable>` became `return <undefined local>`. Nothing about
that function has a hole, and nothing about it is equivalent.

### 7.1 Nothing found proved the method unsound

### 7.2 One thing looked unsound and was not

A/B function counts differ by 26%, which would be fatal if the mint or the
loader were dropping functions. `tools/probes/probe_gap.mjs` ruled it out
with three independent counts of the same text: our emitter claims 230
functions, Babel finds **229** function literals actually present in the text,
and the minted cache carries **76**. The controlled follow-up
(`tools/probes/probe_gap2.mjs`, now self-test F) showed the mint carries 81/81
and 201/201 and 401/401 when the closures are created, and 2/102 when they are
not. The instrument is faithful; the gap is in the output.

### 7.3 Limitations that are real and should be read with the ranking

* **Only the first hunk in a function is independent.** A sequence diff
  attributes everything after the first divergence to the alignment it
  happened to pick, and first-appearance register classes renumber as soon as
  the streams diverge. `register-class` (7 324 functions) and some of
  `reordered-block` and `extra-temp-materialisation` are plausibly consequences
  of an earlier substitution, as §6.6's repro shows directly. The ranking is
  therefore sound as a *work queue* — fixing the top entry will collapse much
  of the tail — and not sound as a claim that 7 324 functions have an
  independent register-allocation problem. Measuring the family of each
  function's FIRST hunk would separate root causes from consequences and is the
  one thing I would add next.
* **`greedy` pairing is circular** — it matches on the similarity being
  measured. It touched 2 pairs here, so it is currently harmless, but it would
  not stay harmless on a corpus where `sfi` coverage is worse.
* **22 pairs were too large to diff** (`n*m > 4e6`); their similarity is
  counted, their divergence is not classified.
* **Literal element values are compared now** (§3.5), but four residuals are
  not: the elements of an all-double array literal
  (`!undecoded:FixedDoubleArrayMap`, because a `FixedDoubleArray`'s stride is
  not in the profile), which declared function a `DeclareGlobals` entry points
  at (`idsOmitted`, because `src/heap` identifies an SFI by per-cache id and
  carries no name), the contents of a container above the inline cap (`hashed`
  — a difference is still detected, just illegible), and a `#<digits>` inside a
  string with an unescaped quote earlier in it. All four are counted per file.
  **Every per-function number in §6 predates this**, and was computed with
  literal values invisible; §6.9 measures the difference.
* **Feedback slot indices are erased to `FB[*]`** — 1 359 236 operands, 0.30
  per instruction. A wrong slot index cannot be detected. This is sound (the
  index is a running counter) but it is an erasure of a value, not of an
  encoding, and it is reported as such.
* **The sample is 25.0% of files and 41.0% of bytes, and the three biggest
  inputs in it produced no comparison** (two decompile aborts at a 1200 MB
  child heap, one 480 s timeout). 54.2% of the stream-A functions the sample
  touched — 54 189 of 102 866 — are in those three files, so the largest
  bundles are absent from every per-function number here. A full-corpus run
  needs a bigger child heap than this host can give.

### 7.4 What the normalisation erased, in numbers

Over stream A's 4 461 514 instructions and 6 071 297 operand fields:

| erased | count | per instruction | tier |
|---|---:|---:|---|
| local register number → identity class | 1 969 996 | 0.442 | encoding |
| feedback slot index → `FB[*]` | 1 359 236 | 0.305 | **value** |
| constant pool index → the value | 997 130 | 0.224 | encoding |
| source position | 1 718 201 | 0.385 | encoding |
| jump delta → label | 245 177 | 0.055 | encoding |
| `.Wide` / `.ExtraWide` | 307 620 | 0.069 | encoding |
| register-range start (length kept) | 120 474 | 0.027 | encoding |
| per-cache object id → `#*` (§3.2) | 121 311 | 0.027 | encoding |
| **total value erased** | **1 359 236** | **0.305** | |
| **total encoding erased** | **3 640 397** | **0.816** | |

Kept, and compared: 280 688 parameter registers, 190 088 special registers,
660 970 non-jump immediates, 207 061 flag immediates, 38 535 runtime/intrinsic
names, every opcode, every operand's arity and kind order, and the handler
table. Stream B's figures are in the raw report.

So: **0.31 value-bearing operand fields erased per instruction, and 0.82
encoding-only**. The honest reading of "8.06% exactly equal" is "equal in
opcode, operand arity and kind, parameter and special registers, immediates,
flags, constant *values*, callee names, def/use relations, control-flow edges
and handler ranges — and not compared on feedback slot indices, literal
element values or declared-name lists."

That last clause is what §3.5 removed, after these numbers were taken.
Literal element values and declared var names **are** compared now, so the
reading of the post-fix rate in §6.9 is the same sentence with "literal
element values or declared-name lists" replaced by "the elements of an
all-double array literal, the identity of a declared function, and the
contents of a container above the inline cap". The raw report carries the
count for each.

### 7.5 The one class counted separately

§3.3's invented closure name is the only candidate for a
"provably-does-not-matter" erasure, and it is kept out of the headline on
purpose. `exactModuloClosureNames` equals `exactFunctions` exactly — **2 896 =
2 896** — so on this sample no function differs only by a name the emitter had
to invent, and the question is moot. `closure-name` does not appear in the
ranked cause list at all.

The other candidate, `o.x` against `o["x"]`, is not a divergence: V8 compiles
both to `GetNamedProperty` because `BytecodeGenerator` classifies the access by
`Property::key()->IsPropertyName()`, which is true for a non-index string
literal. It cannot appear in this measurement, and the 2 functions in
`named-vs-keyed-property` are the genuine case, a computed key.

## 8. Running it

```
node tools/verify/o1_corpus_selftest.mjs
node tools/verify/o1_corpus.mjs --jobs 2 --stride 4 --timeout 600 --child-heap 1200 \
     --work scratch/o1corpus/results --out scratch/o1corpus/O1_CORPUS.md
node tools/verify/o1_corpus.mjs --merge-only --work scratch/o1corpus/results \
     --out scratch/o1corpus/O1_CORPUS.md
```

`--timeout` is in **seconds** and the heap flag is **`--child-heap`**, matching
the other three corpus scanners. The run is resumable: a file whose result JSON
exists is skipped, `--force` redoes everything. `--merge-only` takes its file
list from the **results**, not from the corpus, so a sharded run merges in a
job that never staged the input.

The full corpus needs the cloud. The private corpus repo
`tgwsaki-meow/v8-jsc-corpus` has `.github/workflows/scan.yml`, which takes a
`layer` and shards by bytes with `tools/ci/shard_corpus.mjs`; the per-shard
commands are

```
node tools/ci/shard_corpus.mjs --corpus extracted_jsc --shards 12 --index $I --out /tmp/shard
node tools/verify/o1_corpus.mjs --corpus /tmp/shard --jobs 2 --timeout 1800 \
     --child-heap 1400 --work work/o1 --minter $ELECTRON
```

and the merge job, with every shard's `work/o1` downloaded into one directory,

```
node tools/verify/o1_corpus.mjs --merge-only --work work/o1 --out docs/O1_CORPUS.md
```

The shard job needs an Electron 40.0.0 binary for the runner's platform —
`tools/oracle/fetch_electron.mjs 40.0.0 <platform>` downloads the archive but
extracts only the snapshot blobs, so the binary has to be unpacked as well.
Without it the runner exits 2 rather than minting with the wrong V8.

At the measured rate (260 files, 44.7 MiB, 45 minutes on 2 cores) 12 shards
should put the full 1039 files inside about 20 minutes of wall each.
